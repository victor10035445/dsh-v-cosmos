# cosmos-spec — openspec 的 cosmos 变体范式

> cosmos-spec 是 openspec 工作流的**提示词级**扩展：为提案增加「待创建 → 已创建 →
> 已审核 → 已执行」生命周期状态，供 DSH Cosmos 星系视图渲染提案的真实位置。
> 无新增 CLI 命令、无 npm 依赖——全部状态由变体技能文本在流程节点直写两个旁挂文件。
> 唯一定义点 = [CONTRACT.md](CONTRACT.md)。
>
> 两类许可例外（均由端点不可达时降级跳过、不阻断状态步骤）：
> ① 归档变体技能的可选**「会话扫尾」**步骤调用 cosmos 插件的会话归档 / 前缀改名端点；
> ② explore / ff / 审阅 / apply 变体技能的可选**「关联绑定」**步骤调用
> `POST /api/dsh-v-cosmos/bind-session` 声明本会话的提案工作面（显式绑定优先、启发式
> 回落）。状态契约两个旁挂文件与其余流程主体维持零插件依赖。

## 动机

Cosmos 的核心问题是「我的宇宙现在长什么样、哪里需要我」。原版天体语言只有一层
「扫描推导」的外观表达：恒星颜色来自 tasks.md 勾选进度，看不出一个提案处于
「讨论中 → 已落盘 → 已审核 → 已执行」的哪个位置；「待创建（已建议、尚未落盘）」
的提案更是完全不可见。cosmos-spec 用最小成本补齐这一信息层：

- **恒星颜色 = 生命周期**：待创建（星胚：虚线轮廓+呼吸）/ 已创建（蓝白）/
  已审核（升亮 + 金色印章环）/ 已执行（金色）；
- **执行活跃度走独立热度通道**（白热核 + 十字耀斑），颜色不再承载进度语义。

另一个跨设备痛点：cosmos-spec 及其变体技能随 git 在设备间共享，而技能文本引用的
openspec 技能仓库根路径各设备不同——硬编码本机绝对路径一换设备即断链。为此契约新增
**路径令牌** `OPENSPEC_PATH`（裸前缀占位，见 CONTRACT §9「路径令牌」）：技能文本以
令牌引用技能仓库资源，由承担技能文本加载的机制（现实载体 = cosmos 插件的
SkillProvider）在注入会话前渲染为该设备配置的真实路径。

## 状态机

```
 pending-changes/<slug>.json        changes/<name>/.state.json
 ┌──────────────────────┐     ff     ┌──────────────────────────────────────────┐
 │ 待创建 (proto)        │ ─────────▶ │ 已创建 (created)                          │
 │ 虚线轮廓 + 呼吸        │  写 created │ 蓝白                                     │
 └──────────────────────┘  清理锚点   └──────────────┬───────────────────────────┘
                                                    │ review（tasks 未全勾）
                                                    ▼
                                     ┌──────────────────────────────────────────┐
                                     │ 已审核 (reviewed)  升亮 + 金色印章环        │
                                     └──────────────┬───────────────────────────┘
                                                    │ apply / review（tasks 全勾）
                                                    ▼
                                     ┌──────────────────────────────────────────┐
                                     │ 已执行 (executed)  金色                    │
                                     └──────────────────────────────────────────┘
```

回填规则：审阅/apply 写入前先读 tasks.md 勾选——全勾 → executed，否则 → reviewed；
**只进不退**，显式降级仅用户明确要求。tasks 全勾只是 executed 的**必要条件**：回填另须
通过**主会话收尾门禁**——写入时本会话派生子任务（subagent / 后台任务）均已返回终态
（完成或中断），存在未返回子任务时推迟到全部返回后、最终回复前的最后一步；apply
「进入流程」写入发生在派发之前，天然满足。回填为主会话专属动作，子会话只勾 tasks.md
并返回报告，不得写 `.state.json`。

星胚归并：锚点可选携带 `sessionId`（写入会话 id）——同一探索会话的多个锚点归并为
**一张**星胚合并卡片（卡内逐行列出推荐 slug），缺 `sessionId` 的旧锚点各自成卡。

星胚移除（清理路径三）：人工判断某条建议不用做时，hover 该星胚（proto 恒星）信息卡 →
点「移除星胚」→ 再点确认态按钮（约 3s 无操作自动回弹），宿主即硬删除该锚点单文件
（守卫：同名真实提案目录存在则拒绝；路径穿越 slug 恒拒），星胚以既有低强度消散变体
退场。反悔 = 重建同名锚点（重跑 explore 或手写 JSON），经出生坡道重现。该移除入口是
用户显式动词（非推导写入），是渲染端「对契约文件恒只读」的唯一例外。

## 目录约定

```
<workspace>/
└─ openspec/
   ├─ changes/
   │  └─ <name>/                活跃提案（openspec CLI 原生管理）
   │     ├─ .state.json         ← 契约文件一：生命周期 {version, state, setBy, at}
   │     ├─ proposal.md / design.md / tasks.md / specs/ …（CLI 原生工件，不变）
   │     └─ archive/            归档提案（无需状态——已不在活跃状态）
   └─ pending-changes/          ← 契约文件二：待创建锚点（一文件一条目）
      └─ <slug>.json            {name, by, at, sessionId?}
```

- 两个文件均为 **UTF-8 无 BOM** 的合法 JSON（见 CONTRACT §7 编码纪律）；
- 锚点清理三条路径（CONTRACT §6）：① ff 成功创建提案后由技能自动清理；② 孤儿锚点由
  用户手工清理（删 JSON 或经 Cosmos 星胚信息卡「移除星胚」）；③ 用户显式移除——画布
  星胚信息卡两击确认后由渲染端删除该锚点单文件（仅用户点击驱动、同名提案目录守卫先行）；
- 同名目录存在时渲染端忽略锚点（目录优先），孤儿锚点无害（仅残留一颗星胚）。

## 与 openspec 上游的关系

- **上游零改动**：不修改 openspec CLI、不新增 npm 依赖、不占用其命令面；
  提案目录内的 `.state.json` 与根级 `pending-changes/` 对 CLI 零感知
  （`list` / `status` / `validate` 行为不变——零侵入性质有自动化断言固化）；
- **核心工作流照旧**：scaffold / status / instructions / validate / archive 继续
  调用本机已装的 openspec CLI（技能端唯一前置）；
- cosmos 渲染端（dsh-v-cosmos 插件）对 CLI **零依赖**、对契约文件**恒只读**（唯一例外 =
  用户显式点击「移除星胚」时的锚点单文件删除，见 CONTRACT §6.3）；
  fs.watch 覆盖 `openspec/` 根以秒级同步状态变化（点燃/落印转场跨标签页生效）。

## 迁移语义

- 状态随**提案目录**走：工作区迁移到新设备（git clone / 网盘同步）后重新扫描，
  恒星骨架连同 `.state.json` 生命周期一并重建——状态不依赖本机插件存储；
- 存量提案（无 `.state.json`）零动作，一律按「已创建」渲染；审阅/apply 技能
  首次触碰即按 tasks 回填；
- 回滚 = revert 渲染端提交；磁盘上的契约文件残留无害（旧渲染器不读、新渲染器
  按契约读）。

## 变体技能（skills/）

| 技能 | 状态动作 |
|---|---|
| `cosmos-explore` | 探索结论建议创建提案时写 `pending-changes/<slug>.json` 锚点（含写入会话 `sessionId`，同一探索会话的锚点在面板归并呈现为一张星胚卡片）；可选「关联绑定」：全部建议 slug 一次绑定 |
| `cosmos-ff-change` | 创建（补全全量 artifacts）+ 创建成功写 `.state.json`（created）+ 以所建提案名清理锚点；可选「关联绑定」：本次创建的全部提案一次绑定 |
| `cosmos-review` | 审阅回填（经收尾门禁）：tasks 未全勾 → reviewed；全勾 → executed；可选「关联绑定」：收尾绑定本提案 |
| `cosmos-apply-change` | 进入流程时（派发前，门禁天然满足）按 tasks 回填 executed；收尾时经门禁回填（只进不退）；可选「关联绑定」：收尾绑定本次流程涉及的全部提案 |
| `cosmos-archive-change` | 无需状态动作（归档提案不渲染恒星）；可选「会话扫尾」——经插件端点批量归档关联会话 + 自改名 `已归档-`（端点不可达 → 跳过并注明，不阻断归档） |

四技能的「关联绑定」步骤调用同一端点（`POST /api/dsh-v-cosmos/bind-session`，
**替换**语义——清单即会话当前工作面）：端点不可达或失败时降级为跳过并在回复注明，
MUST NOT 阻断状态步骤；绑定属于可视化纠偏，退回启发式只影响星图关联度，不影响任何
提案状态。

技能定义标注基于的 openspec 世代（`generatedBy`）与契约版本；**映射接线**（哪个
环境加载哪些变体技能）属于部署配置，不在 cosmos-spec 内约束——按需将
`skills/*.md` 复制/链接到你的技能目录，并保证 `cosmos-spec/CONTRACT.md` 可被引用。

**令牌渲染与接线**：优先经 cosmos 插件 provider 加载变体技能——provider 在技能文本
注入会话前渲染 `OPENSPEC_PATH` 令牌为该设备配置路径（CONTRACT §9）。令牌值语义 =
包含 `openspec-*` 技能束的技能目录根（本机示例 `…\dsh-v-skill-links\.trae\skills`）；
**手工接线**部署（复制/链接技能文本、无渲染机制）两条出路明示——自备等价令牌渲染
（接线期自行展开令牌），或接受**未解析降级**：正文原样注入 + 明显的未解析警示行，
不报错、不阻断。令牌 MUST NOT 进入持久工件：
技能写 proposal / tasks 等落盘文档时须写解析后的真实路径或相对路径（CONTRACT §9
持久工件禁令）。

**读取兜底与状态化警示**：模型照抄令牌路径的常见失败调用全部被插件兜底捕获（路径类
工具 read/write/edit 与 str_replace_editor、glob/grep 的 `path` 与 `pattern` 键、
bash/pwsh 命令串——命令类只要求令牌在命令串内出现，零命中的 glob/grep 不拦截）——
调用失败（isError）时返回一次纠正反馈，附解析后的绝对路径与「cosmos-spec 技能目录
扫描根」提示行（已配置与未配置分支均适用，模型一次定位技能文件、无需漫游搜索）；
未配置降级警示行区分「未配置」与「配置存在但读取异常（共享配置存储装载失败，详见
插件日志）」，两态均携带设置-cosmos「通用」页签的 `openspecPath` 设置入口，存储装载
失败另在插件日志 warn 一次。
